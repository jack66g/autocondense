# 上下文压缩机制调研（2026-10）

> 目的：摸清市面各家的上下文压缩逻辑，对照 autocondense v0.2.0 找差距与优化方向。
> 结论先行：**市面全是"宿主内建、阈值触发、单摘要替换"；autocondense 的"LLM 判定 + 分段画像入库 + 宿主外挂"路线在市面没有同类**，方向正确；主要差距在恢复策略、真实水位、增量摘要三处，均可落地。

## 一、市面机制全景

### 1.1 单摘要替换式（主流：全量 compaction）

| 工具 | 触发 | 摘要策略 | 压缩后保留 |
| --- | --- | --- | --- |
| Claude Code | 自动 ~95% 水位 + 手动 /compact（可附焦点指令、项目级 Compact Instructions） | 模型自写结构化摘要（意图/决策/文件/错误与修复/待办/下一步） | 边界标记→摘要→**重读最近 5 个文件**→todos→plan 状态→hook 注入→"继续"消息 |
| Codex CLI | 按模型 token 阈值（180k/244k 不等，95% 安全边距） | 专用 handoff 提示词（"给下一个接手的 LLM 写交接"） | 初始上下文 + **最近 ~20k tokens 的用户消息** + 摘要（带 summary_prefix 说明） |
| Gemini CLI | 可配置窗口百分比，/compress | 结构化摘要，整段替换聊天上下文 | 摘要 + 会话继续 |
| OpenCode | isOverflow()（token 超 context-output 限额） | 压缩系统提示 + 详细摘要；自动压缩后追加"如有下一步请继续" | 摘要 + 最近保护带（见 1.2 prune） |

各家共同的经验教训：
- **95% 触发偏晚**，社区共识 85-90% 更稳（Claude 用户反馈任务中压缩会"跑偏"）；
- **多次压缩累积损耗**：Claude 与 Codex 都明确警告质量衰减，Codex 压缩失败还有指数退避重试；
- 摘要模板五要素高度趋同：**完成/进行中/文件/下一步/约束与决策**——与我们七章节模板吻合。

### 1.2 分层/渐进式（更先进的做法）

- **工具输出层先清**：
  - Claude Code **microcompaction**：大工具输出（Read/Bash/Grep…）"热尾"保留近期少量，其余落磁盘只留路径引用（冷存储可回读）；
  - **OpenCode prune**（独立于压缩的机制）：保护最近 40k tokens 工具输出，可剪部分 >20k 才动手剪；
  - **Anthropic Context Editing API**（`clear_tool_uses_20250919`）：达到 trigger 阈值自动清旧工具结果、keep 最近 N 条，且清理前给模型**预警让它先摘录关键信息**；缓存副作用：清早期内容会作废后续缓存，写在缓存断点前则更省。
- **增量 delta 摘要**：Claude 后台代理每步只写 1-2 句增量更新，**基于前次摘要而非重读全文**——直接对冲"多次压缩累积损耗"。
- **Manus 路线**（KV-cache 优先）：KV-cache 命中率是第一指标（成本差可达 10×）；上下文 append-only、文件系统当外部记忆、已知事实不入 prompt。

### 1.3 不压缩、靠结构（Amp / Sourcegraph）

短会话哲学 + 手动工具族：**Handoff**（指定下个任务目标，用副模型从旧线程提取相关信息生成新线程开场）、Fork（复制上下文快照点）、Thread References（按需引用别的线程）。适合人驱动的工作流，不适合 24h 无人值守。

### 1.4 学术侧

**Context Compaction Theory（arXiv 2608.01326，2026-08）**——最有分量的理论结果：

- 把压缩形式化为"查询到来**之前**的预算保留决策"：查询无法影响压缩，所以信息损失不可避免；
- 证明"生成（LLM 摘要）"严格强于"选择（裁剪/子集）"，二者存在 Θ(log n) 分离；
- **关键实证**：15,000 条 URL 的集合成员查询，用 Anthropic 压缩端点摘要后错误率 0.505-0.555（≈随机猜）——**摘要保持的是"工作状态/要点"，可枚举的事实几乎全丢**；同预算 Bloom filter 只有 1/3 错误，全量保留仅 0.02；
- 对我们的直接指导：**可枚举细节（文件清单、接口签名、数据点）绝不能指望摘要承载，必须外置到可查询存储（快照文件/SME 分段），摘要只承载工作状态，恢复靠按需查询而非塞满上下文**——我们的"恢复指针 + 分段画像 + Read 完整快照"设计恰好是这个结论的正确实现，且我们比市面多做了一层：恢复时可检索（市面摘要没有查询面）。

其余（与我们关系弱，了解即可）：LLMLingua / LLMLingua-2（token 级提示压缩，2-5×，比人工快 3-6×）、AutoCompressor / ICAE / gist tokens（学习型软压缩）。这些面向 prompt 静态压缩，agent 会话压缩领域目前实际用的还是"LLM 写摘要"。

### 1.5 记忆系统侧（压缩的"存档面"）

Letta/MemGPT（操作系统式分页记忆，agent 自编辑 memory blocks）、mem0（事实抽取 + 混合检索，p95 检索 0.2s）、Zep/Graphiti（时序知识图谱，LongMemEval +18.5%）。各家基准互相打架，但共识是：**记忆要按语义单元存取，不要整篇 blob**——我们的分段画像正是这个方向。

## 二、autocondense 的定位与差异

**市面没有同类的东西（我们的优势）：**
1. **LLM 判定环节**：所有工具都是水位/轮次硬阈值触发，没有一家做"任务是否收尾、压缩影响多大"的语义判定。我们的 judge 表（task_finished/impact/safe + normal/urgent 矩阵 + 延迟窗口）是独有的，且正好落实"任务边界优先压缩"的社区最佳实践——只不过别人靠人手动 /compact 实现，我们自动化了。
2. **分段画像入库**：市面摘要都是一团 blob 塞回新上下文；我们把摘要拆成语义单元进可检索记忆库（SME），可逐条强化、跨会话检索。
3. **宿主外挂、跨工具**：内建压缩每家一套；我们不替代宿主压缩，而是"压缩前抢救存档 + 判定时机 + 压缩后恢复注入"，一套逻辑适配所有 MCP 宿主。
4. **摘要校验与重提交**：章节校验失败给中文错误清单让模型重写——市面没有质量闸。

**差距（按影响排序）：**

| # | 差距 | 市面参照 | 影响 |
| --- | --- | --- | --- |
| 1 | 恢复是"截断注入"（≤8000 字符） | Claude Code：摘要+**重读最近 5 文件**+todos 按需恢复 | 恢复后模型要自己重摸文件，浪费轮次 |
| 2 | 水位靠 transcript 启发式估算（CJK×1+其他×0.25） | 各家都用宿主真实 token 计数 | 估不准 → 判定时机偏差 |
| 3 | 每次全量写 digest | Claude 后台代理 delta 摘要 | 多次压缩累积损耗 |
| 4 | 无工具输出层控制 | microcompact / prune / context editing | 插件层做不到（需宿主/API 配合），只能靠 PreCompact/水位前置存档缓解 |
| 5 | commit 分段写 SME 慢（15 段≈50s，逐条嵌入） | — | 超时风险、阻塞 |
| 6 | 重复段不去重 | mem0 的 upsert/更新语义 | 同项目多次 commit 相似段落重复入库 |

## 三、模型适配评估

**已经做对的：**
- digest 由干活模型自己写——模型无关，天然适配各家；
- 判定表是 low/medium/high 三选一+布尔——对模型指令遵循能力要求极低；
- `usable_context_tokens` 可配——1M 窗口模型（Gemini 等）下水位规则自动退位给任务边界/轮次规则；
- CJK×1 系数对中文会话估算友好；
- 章节校验+重提交兜住弱模型的模板偏离。

**弱点：**
1. token 估算不分 tokenizer（GPT/Claude/Gemini/GLM 分词差异可达 20%+）；应优先用宿主 hook 上报的真实 `context_tokens`，估算只做兜底。
2. 长窗口模型下"轮次"信号偏弱（25 轮可能才用 10% 上下文）——此时任务边界规则是主力，行为正确但可加"绝对 token 距离"参数。
3. 摘要质量随模型能力波动，但校验闸能兜底，属可接受。

## 四、优化方案（建议排期）

### P0：小改动、直接补差距

1. **恢复包按需化**：restore 输出按预算分配优先级（未完成 > 恢复指针 > 决策/坑 > 已完成），并在恢复指令中明确"按文件变更清单重读关键文件"——对齐 Claude Code 的重读最近 5 文件。
2. **水位真实化**：hook 事件（PostToolUse/Stop/SessionStart）带的 `context_tokens` 优先入库，启发式估算仅在缺失时兜底。
3. **SME 批量提交**：`store_segments` 改走 SME 的 `POST /memories/batch`，一次往返，commit 50s → 预计 <10s。
4. **段去重/强化**：入库前对相似段查 SME（同项目近 N 天），高相似改为 reinforce 已有段而非新增。

### P1：结构优化

5. **增量 delta 摘要**：项目已有前次快照时，begin 返回模板+前次摘要，指引只写增量；恢复时拼 delta 链，每 N 次合并为全量——对冲累积损耗。
6. **完成信号扩展**：判定输入加入"最近 N 轮无文件修改/无失败/无用户新指令"等完成侧信号（不只依赖计划清空）。
7. **延迟退避**：DEFERRED 后若下轮又立即候选，defer 窗口指数延长（5→10→20 轮），防判定乒乓。

### P2：为自研宿主储备

8. **三层压缩架构**：自研宿主时打通 microcompact（工具结果落盘留指针——快照文件机制可直接复用为冷存储）+ 会话层压缩（autocondense）+ 记忆层（SME 分段画像），这是 Claude Code+Manus 路线的合体。
9. **KV-cache 感知**：宿主能提供缓存断点信息时，压缩点对齐断点执行（现在任务边界触发天然接近断点，已是近似最优）。
10. **判定表增强**：加 confidence 字段 + 服务端回填"距水位到顶预计还有 X 轮"，给模型更充分的决策依据。
