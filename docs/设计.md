# autocondense 设计要点

本文固化核心层与接入层的设计决策。REST 契约见 [CONTRACT.md](CONTRACT.md)，接入操作见 [接入.md](接入.md)。

## 1. 双层兼容架构：常驻服务 + 薄代理接入层

```
宿主 ──MCP(stdio)──> mcp_server.py ──┐
宿主 ──hooks(stdin)─> ac_hook.py ────┼──HTTP──> autocondense.service（FastAPI，唯一落盘方）
                                      │              │
                                      │        ~/.autocondense/（原子写）
                                      └        SME 记忆插件（可选，默认 8000）
```

- **常驻 REST 服务是唯一的判定与落盘方**：MCP 进程和钩子进程都是无状态薄代理。这样同一项目里
  多个智能体/多个 MCP 进程/钩子并发写入不会出现多进程抢写同一快照文件；服务内存态即真相，
  持久化集中在 ~/.autocondense/（全部原子写：tmp + os.replace）。
- **接入层两种通道、互为补充**：MCP 工具面向智能体的主动调用（判定的 action_hint、判定表、
  next_instruction 原文带回，闭环靠智能体执行）；hooks 面向宿主的被动事件（TodoWrite 追计划、
  Edit/Write 记文件活动轮、PostToolUseFailure 记失败轮（ZCode 独有）、Stop 拦停、
  SessionStart 注入恢复、PreCompact 记冷却——PreCompact 仅 Claude Code 支持，ZCode 侧不注册该钩子）。
  只用其一也能工作，两者叠加体验最佳。
- **惰性拉起**：MCP 服务器不预启服务，首次工具调用 `_ensure_service()` 探活（GET /health，3s 超时）
  → 不在则单飞锁 + 双检后 `Popen([sys.executable, "-m", "autocondense.service", ...])`
  （Windows `DETACHED_PROCESS|CREATE_NEW_PROCESS_GROUP`，POSIX `start_new_session=True`，
  stdout/stderr 追加 `%TEMP%/autocondense_service.log` 且父进程立即关句柄）→ 锁外每 0.5s 轮询
  最多 30s（无模型加载，秒级起）；超时 RuntimeError 指向日志路径。
  已知边界：Windows 下 MCP 客户端退出时可能树杀进程带走分离服务——无害，下次调用自动重拉。
- **所有 httpx 请求 `trust_env=False`**：系统代理会劫持 localhost。
- **全自动开关**：`enabled=true`（默认）全自动零提示零确认；`enabled=false` 一切判定 NO、完全不干预。
  不存在「询问用户是否压缩」的环节——manual/auto 双模式已删除。

## 2. 候选制判定：规则层 + 大模型判定环节

### 2.1 规则层只产生「候选」（顺序固定，见 signals.decide）

| 序 | 条件 | 结果 |
| --- | --- | --- |
| 1 | plan_in_progress > 0 | NO（任务连续性绝对优先） |
| 2 | 冷却未过 | NO |
| 3 | 计划全部完成 | 候选 / plan_done |
| 4 | completed 条目跨度 ≥ task_min_rounds（含归档） | 候选 / task_done |
| 5 | 水位 ≥ water_threshold | 候选 / water_level |
| 6 | 连续 idle_signal_rounds 轮无文件修改与失败（活动记录存在时） | 候选 / idle |
| 7 | 距上次压缩 ≥ turns_threshold 轮 | 候选 / turns |
| 8 | 否则 | NO |

规则命中候选时服务返回 `should="JUDGE"` 并附轻量判定表（judgment_form），由调用方（智能体本身即
大模型）立即填表提交 `POST /judge`。顺序即设计：先保证不打断（1/2），再找「任务脉络闭环」的最佳
时机（3/4），再兜底资源压力（5），再捕捉「疑似任务停歇」（6，不用计划工具的会话也有边界信号），
最后温和建议（7）。token 口径（v0.3.0 起真实化）：**智能体上报的 context_tokens 优先**（10 轮保鲜，
signals.token_source="reported"），缺失或过期才回落 transcript 逐行 `CJK×1 + 其他×0.25` 估算
（token_source="estimated"）；由 {turn, tokens} 采样另估 `rounds_to_full` 随判定响应下发（informational）。
水位阈值本身粗粒度（0.7），精确 tokenize 无意义还引入依赖。

### 2.2 判定环节：为什么先轻量判定、再写摘要

写一份合格摘要要读全上下文、要几百 token 的输出，是整条链路里最贵的动作。规则层只有量信号
（计划数/轮次/水位），不知道「任务是不是真的告一段落」「现在压会不会打断思路」——直接压会浪费，
直接放弃又会在水位危急时错过存档窗口。因此在规则与摘要之间插入一张**五字段轻量判定表**：
`task_finished / impact / impact_reason / safe_to_compress / reason`，由正在会话里的大模型自评
（它对任务状态的理解比任何规则都准），一次调用几 token，把「要不要花大钱写摘要」变成廉价决策。

**判定矩阵（urgent 与 normal 的差异）**：

- `normal`：`safe_to_compress 且 task_finished 且 impact == low` 才通过——不急，只在任务收尾、
  影响最小的完美时机压；
- `urgent`（水位 ≥0.85）：`safe_to_compress 且 impact != high` 即通过，**任务未完成也可压**——
  水位危急时宿主随时会有损强压，自己先存档一份结构化快照是净收益，完美时机反而不可求。

### 2.3 延迟窗口：防乒乓

判定不通过（DEFERRED）时设 `defer_until_turn = 当前轮次 + min(judge_defer_turns × 2^defer_streak,
judge_defer_max_turns)`（默认 5 → 10 → 20 封顶的指数退避；连续不过时骚扰成本递减），窗口内候选
判定一律 NO——否则「候选命中→判定不过→下一轮又命中」会在每轮 Stop 上反复骚扰。窗口只是
**暂停再判定**而非放弃：到期自动重新评估；urgent 候选可无视窗口（水位危急等不起）；
判定通过或 commit 成功后窗口清空、退避计数 defer_streak 归零。

## 3. 防抖四闸（不会反复骚扰/重复压缩）

1. **冷却**：commit 或 PreCompact 后 `cooldown_until = now + cooldown_minutes`，期内一切 NO。
2. **消费即清账**：commit 后当前 completed 条目清除且**不进归档**（已被本次压缩覆盖，再归档会在
   冷却结束后重复触发 task_done）；`mark_condensed` 清空 plan_archive。
3. **归档语义**：从计划里消失的 completed 条目进 `plan_archive` 保留跨度供规则 4；pending/
   in_progress 消失即丢弃（用户删掉的待办不算完成）。
4. **判定延迟窗口**：见 §2.3，DEFERRED 后 5 轮内不再进判定。

另有 Stop 钩子侧的**闩锁**（见 §6）。

## 4. 恢复注入：压缩后无损续命

- 快照按项目（`sha1(normcase(resolve(cwd)))[:10]`）组织在 `~/.autocondense/snapshots/{hash}/`，
  index.json 最新在前。
- `build_restore_payload`（v0.3.0 起按需打包）：不再「最新快照全文一刀切」，而是按优先级装入
  `restore_max_chars` 预算——未完成/恢复指针整节最优先，决策/坑逐条（≤200 字符、≤10 条），
  目标 ≤300 字符，已完成每条一行（≤80 字符、≤10 条），超预算低优先级先丢，截断给 `full_file` 指针。
  对标 Claude Code「摘要 + 重读最近文件」：同时从文件变更清单解析 `reread_files`（前
  `restore_reread_files` 条）与 `todo_open`，`/restore` 据此生成 `next_actions`（先重读关键文件再续未完成）。
- delta 链合并：项目存在连续增量快照时，先沿链（深度上限 `delta_merge_every`+1）合并成完整状态
  （未完成/指针/目标取最新非空，bullet 类并集去重）再打包；链不完整则只用最新快照兜底。
- 注入路径：宿主 SessionStart(compact|clear|resume) → 钩子取 `additional_context` 包成
  `{"additionalContext": 文本}` 一行 JSON 打到 stdout（UTF-8 字节直写，绕开 Windows 控制台编码）；
  截到 9000 字符，截断则末尾追加「完整快照：{full_file}，需要时用 Read 读取」。
- MCP 侧等价工具 `condense_restore`（智能体主动调，返回文本 + SME 检索摘要）。

## 5. SME 桥接：分段画像、可选、可降级、永不阻断

- commit 时不再整篇入库：`split_digest` 把摘要按章节拆成**多条语义段**（goal / accomplishment /
  todo / decision / pitfall / file_change / restore_pointer / misc，各带独立 tags 与 0.5-0.8 的
  importance）。每条已完成、待办、决策、踩坑独立成段，SME 的 Ebbinghaus
  强化可以**逐条**命中，而不是只能检索到一整篇快照；段数超 `sme.max_segments`（默认 15）按
  重要度合并溢出段。
- 写入路径（v0.3.0）：先逐段查重（score ≥ `sme.dedup_threshold` 且 project+segment_type 匹配 →
  `POST /memories/{id}/hit` 强化旧段而非重复新增，~10s 软预算防拖慢），剩余新段 ≥2 条走
  `POST /memories/batch` 一次往返（该端点不返回各条 id，`sme.memory_id=null` 不是失败），异常
  回落逐条 POST。查重全命中时不做整篇兜底（防同内容重复入库）。
- 兜底链：SME 不在线（health 预检缓存 60s，避免 max_segments 次独立超时拖慢 commit）或分段
  全失败 → 整篇 `store_digest` 兜底；再失败 → 只落本地快照。任何一级失败都不阻塞 commit、
  不影响判定。
- restore 时按 query/项目名检索，客户端过滤 tags 含 `session_digest` 的结果；分段 text 自带
  `[autocondense|project|ts|trigger]` 前缀，天然可检索。

## 6. 钩子的安全纪律与闩锁防死循环

- **绝不干扰宿主**：3s 超时；服务不在线/JSON 坏/stdin 乱码/任何异常 → 静默 exit 0；
  诊断日志一行到 `%TEMP%/autocondense_hook.log`。stdin 按原始字节读再 UTF-8 容错解码。
- **Stop block 的死循环风险**：宿主对 Stop 的 block 会强制模型继续，若每次 Stop 都 block 就是
  死循环。闩锁：block 时写 `~/.autocondense/hook-latch/{session_id}.json` 记 last_block_ts，
  **15 分钟内同一会话只 block 一次**；闩锁自身 IO 失败不拦截 block（宁可多一次提示也不吞掉判定），
  但正常路径下足以断开循环。
- **事件差异化**：PostToolUse/PostToolUseFailure/PreCompact 无输出（服务端记账：计划/活动轮/
  失败轮/冷却）；只有 SessionStart（有快照）和
  Stop（should=JUDGE 且带 instruction）才产生输出。Stop 的 instruction 由服务端生成
  （「立即调用 condense_judge 提交判定，不要询问用户……」），钩子只透传，不自己拼文案。

## 7. MCP 会话映射：宿主不知道自己的 session_id

宿主智能体通常拿不到自己的 session_id，但一定知道工作目录。mcp_server 维护
`~/.autocondense/mcp-session-map.json` `{project_hash → session_id}`（原子写，损坏容忍为空重来）：
首次对某 cwd 调用自动 `POST /session/start`（`mcp-{hash[:8]}-{uuid4}`）并记入映射，后续复用；
显式传 session_id 则优先。钩子侧无需映射——宿主 hooks 事件本身携带 session_id。

## 8. installer 的安全写入

- 默认 dry-run 只打 unified diff；`--yes` 才落盘；写前 `*.bak-autocondense-{时间戳}` 备份。
- 深合并不删别人的条目；幂等（重跑先摘旧 autocondense 条目再写新）；损坏 JSON 跳过该文件并告警。
- `--uninstall` 按我们写入的键名摘除；摘空的容器（mcp.servers/hooks.events）连壳清理；
  被我们新建且只剩我们条目的文件直接删除。
- codex TOML 无标准库解析 → 文本级插入/摘除，块带 `# >>> autocondense` 标记，
  只处理自己的块（手工写的同名表不动——局限已在 --help 与文档注明）。
- `--home` 注入使全部路径可测试化，测试与冒烟绝不碰真实用户配置。

## 9. 数据目录与容错

`AUTOCONDENSE_DATA_DIR` > 用户级 `~/.autocondense/`（与代码位置解耦：插件更新换缓存目录不丢数据）。坏文件（config/sessions-state/index）改名
`.corrupt-{时间戳}` 保留现场后回落默认/清空重来，服务永不因坏数据拒绝启动。
事件流水 sessions.jsonl 追加写，坏行跳过。

## 10. 测试策略

- 核心层：TestClient 全链路 + 线程内 SME stub；判定矩阵全分支、延迟窗口、enabled 开关、
  分段写入端到端（含拆段关闭/全失败兜底）。
- 接入层：mcp_proxy 线程内真服务 + 直接调工具函数 + monkeypatch 验证单飞/轮询/超时；
  hooks 用 subprocess 真跑脚本喂 stdin（覆盖闩锁/截断/离线静默）；installer 全程 `--home` tmp。
- 插件/文档一致性：manifest 版本与组件、SKILL/命令措辞（无先问用户/manual 残留）、
  CONTRACT 含 /judge 契约。
- 真实冒烟：mcp stdio 客户端 initialize→tools/list→call_tool；钩子管道逐事件；installer tmp HOME 装卸。\r

  （每 5 份强制全量，对冲多次压缩累积衰减）；idle 完成信号（PostToolUseFailure + 文件活动轮）；
  DEFERRED 指数退避（5→10→20 封顶）；判定表可选 confidence。各项细节已并入上文对应章节。
- **v0.2.0**：全自动重构——删除 manual/auto 双模式与一切询问交互（enabled 开关语义）；候选制 +
  POST /judge 大模型判定表（normal/urgent 矩阵）；digest 分段画像写入 SME；插件更新后的版本接管
  （service.pid + 健康握手，绝不盲杀）。
